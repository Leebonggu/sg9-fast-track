# 후원금 은행거래내역 일괄업로드 기능 설계

## 개요

현재 후원금은 관리자가 은행 거래내역 xls를 받아 스크립트로 수동 파싱·등록하고 있다(2026-07-02, 198건+19건 실제 처리). 이 흐름을 `/unified`에서 반복 사용 가능한 UI 기능으로 만든다: xls 업로드 → 파싱 → 기존 등록건과 대조 → 신규건만 미리보기 확인 후 등록.

핵심 제약 3가지 (오늘 실제 데이터로 검증됨):
1. 은행이 주는 거래내역의 "보낸분/받는분" 텍스트는 계좌주가 직접 입력한 자유 텍스트라 동/호수 표기 형식이 계속 늘어난다(`동`+`호`, `/`, `-`, `_`, `__`, 전각공백, 이름이 앞/뒤에 붙음, 은행 UI 표시글자수 제한으로 인한 말림 등). **패턴은 앞으로도 계속 새로 나온다** — 하드코딩 1회성 파서가 아니라 패턴을 계속 추가해나갈 수 있는 구조+ 회귀 테스트가 필요하다.
2. 같은 파일 안에 이전에 이미 등록한 거래와 새 거래가 섞여 온다(은행 거래내역은 항상 전체 누적 다운로드). 중복 없이 신규만 골라내야 한다.
3. 중복판단 키(거래시각+금액)만으로는 극히 드물게 콜리전 가능성이 있다 — 실제 서로 다른 두 세대가 같은 초에 같은 금액을 낼 수도 있음. 동/호수로 2차 검증이 필요하지만, 동/호수 파싱 자체가 100% 신뢰할 수 없으므로 이 2차 검증은 "확실한 중복 자동제외"가 아니라 "불일치시 사람에게 확인 요청"으로 설계한다.

## 파서 설계

`web/src/lib/donation-parser.ts` (신규, 순수 함수):

```ts
interface ParseResult { dong: string; ho: string; source: 'memo' | 'sender' | 'fail' }
function extractDongHo(text: string): { dong: string; ho: string } | null
function parseTransactionRow(sender: string, memo: string): ParseResult
```

알고리즘 (오늘 217건 원본 데이터로 검증 완료, 성공률 99%):
1. `memo`와 `sender` 각각에 대해 숫자만 추출(`replace(/[^0-9]/g, '')`)
2. 추출된 숫자열 길이가 4~7자리이고, 앞 3자리가 `BUILDING_CONFIG`에 존재하는 동 번호(901~923)면 앞 3자리=동, 나머지(1~4자리)=호수로 채택
3. **memo 파싱이 성공하면 memo를 우선 채택**, memo가 없거나 실패하면 sender 결과를 채택. (처음엔 sender 우선으로 짰다가, 은행 UI가 발신인 텍스트를 표시글자수 제한으로 잘라내는 사례를 오늘 6건 발견해서 순서를 뒤집었다 — 예: "이춘자 910-50"(sender, 잘림) vs "910/505"(memo, 정확). 단, memo도 100% 정확하진 않으므로 — 절대적 신뢰 X, 아래 2차 검증 참고)
4. 둘 다 실패하면 `source: 'fail'`, dong/ho 빈 문자열 — 미리보기에서 수기 입력 대상

**패턴을 계속 쌓아가는 구조**: 이 알고리즘(숫자추출+동번호검증)은 이미 상당히 일반적이라 대부분의 신규 패턴을 규칙 변경 없이 흡수한다. 그럼에도 흡수 안 되는 새 패턴이 나오면(예: 동 번호가 숫자가 아닌 다른 표기, 완전히 다른 자유서식) `donation-parser.ts`에 케이스를 회귀 테스트로 추가하고 필요시 알고리즘을 보강한다 — 아래 테스트 전략 참고.

## 중복 판단 로직

`web/src/lib/donation.ts`에 추가:

```ts
function buildDedupKey(isoTimestamp: string, amount: number): string // `${iso}|${amount}`
async function getExistingDonationsByKey(): Promise<Map<string, { dong: string; ho: string }>>
```

업로드된 각 거래를 3가지로 분류:

| 분류 | 조건 | 미리보기 처리 |
|---|---|---|
| `new` | 중복키(시각+금액)가 기존 후원금 시트에 없음 | 기본 펼침, 등록 대상으로 체크됨, 동/호수 inline 수정 가능 |
| `duplicate` | 중복키 일치 + (신규 파싱 동/호수가 기존값과 같거나, 신규 파싱이 실패) | 기본 접힘, 개수만 표시, 등록 대상에서 제외 |
| `review` | 중복키는 일치하는데 신규 파싱 동/호수가 기존 등록값과 다름 | 기본 펼침, 기존값 vs 신규파싱값 나란히 표시, 기본은 미체크(등록 안 함) — 관리자가 판단해서 체크하면 등록 |

이 분류는 오늘 실제로 검증했다: 217건 중 198건이 기존 후원금 시트와 중복키 일치, 그 중 7건은 파싱 결과가 기존값과 달랐다(대부분 sender 절단 때문 — memo 우선순위 적용 후에는 재현되는지 회귀 테스트로 고정). `review` 버킷이 바로 이런 케이스를 사람에게 넘기는 안전장치다.

## UI 흐름

새 페이지 `/unified/donations-import` (기존 페이지처럼 `AdminLayout`으로 감싸 세션 인증 재사용, 별도 인증 체계 안 만듦):

1. 파일 선택 input (xls/xlsx) + "미리보기" 버튼
2. 서버가 파싱+분류만 수행(시트에 아직 안 씀), 결과 JSON 반환
3. 미리보기 화면:
   - 상단 요약: 신규 N건(합계 금액) / 확인필요 M건 / 이미등록 K건(자동제외)
   - **신규** 섹션: 표 형태, 각 행 시각/동/호수(수정가능 input)/금액/원본텍스트, 체크박스(기본 체크)
   - **확인필요** 섹션: 표 형태, 시각/금액/기존동호수/신규파싱동호수(수정가능 input)/원본텍스트, 체크박스(기본 미체크)
   - **이미등록** 섹션: 접힌 상태, 펼치면 목록(읽기전용)
4. "등록" 버튼 클릭 → 체크된 행(동/호수가 채워진 것만 등록 가능, 빈 값이면 비활성화)을 서버로 전송
5. 서버가 등록 직전 중복키 재검증(동시 업로드/중복 클릭 대비) 후 `후원금` 시트에 addRows, 결과(성공 건수) 표시

## API

- `POST /api/unified/donations/import/preview`
  - multipart file upload, xlsx 패키지로 서버 파싱 (기존 `downloadAsXlsx`와 동일 패키지 재사용)
  - 예상 컬럼(거래일시/보낸분·받는분/입금액, memo는 optional) 없으면 400 에러
  - 응답: `{ new: [...], review: [...], duplicateCount: number, duplicates: [...] }`
- `POST /api/unified/donations/import/commit`
  - body: 등록할 레코드 배열(관리자가 미리보기에서 확정한 동/호수/금액/시각 포함)
  - 서버에서 다시 한번 중복키 대조 → 이미 존재하면 skip하고 결과에 표시, 나머지 `addRows`
  - `등록자`: 세션에 `operatorName`이 있으면 `"엑셀 일괄등록(이름)"`, 없으면 `"엑셀 일괄등록"` (오늘 처리한 198건과 동일 문자열 유지, 이름만 있으면 붙임)

## 데이터 레이어 (`web/src/lib/donation.ts` 확장)

- `getExistingDonationsByKey()`: 후원금 시트 전체를 `${시각}|${금액}` 키로 Map화 (dedup 대조용)
- `bulkAddDonations(records: NewDonationRecord[], registrant: string)`: commit 단계에서 실제 addRows, 각 레코드에 ID 생성 + `시각`은 원본 송금시각 그대로 보존(오늘 정한 원칙 유지, `addDonation()`의 "시각=지금" 로직과는 다른 별도 함수)

## 테스트 전략

`web/src/lib/donation-parser.test.ts` (신규):
- 오늘 두 파일(공지.xls, 국민은행자료다운.xls)에서 실제로 나온 모든 sender/memo 텍스트 패턴을 fixture로 고정하고 기대 (dong, ho) 출력과 함께 저장 — 최소 20개 이상 케이스(정상 형식 5종 이상, 은행 절단 케이스 5건, 파싱실패 2건 포함)
- 새 패턴이 나올 때마다 이 fixture에 케이스 추가 → `npm test`로 기존 패턴 회귀 여부 확인 (recon-sim의 PDF 회귀 테스트와 동일한 원칙)
- 중복분류 로직(`new`/`duplicate`/`review`) 유닛 테스트: 오늘 검증한 198건 dup + 19건 new + 7건 review 케이스를 그대로 고정 fixture화해서 회귀 테스트로 사용 가능

## 에러 처리

- xls/xlsx가 아니거나 예상 컬럼이 없는 파일 → 업로드 단계에서 명확한 에러 메시지, 시트 접근 안 함
- 빈 파일(헤더만 있음) → "처리할 거래가 없습니다" 안내
- commit 시 이미 등록된 게 재확인되면(레이스 컨디션) 자동 skip하고 최종 결과에 몇 건 skip됐는지 표시

## 주의사항

- 파싱 실패/불일치(`review`) 건을 강제로 자동 등록하지 않는다 — 후원금은 금전 기록이라 애매하면 반드시 사람이 확인하게 한다.
- `review` 버킷이 계속 크게 나오면(파서 정확도가 떨어지면) 그 자체가 패턴 추가가 필요하다는 신호로 보고 `donation-parser.ts`를 보강한다.
